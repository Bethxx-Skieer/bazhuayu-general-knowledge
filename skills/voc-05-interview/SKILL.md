# 用户访谈 VOC 结构化分析

**English name:** User Interview VOC Analysis

把访谈文本系统化为可回溯的主题、用户故事、需求、动机、痛点和旅程洞察。

## First-use introduction

**MUST：当前会话/任务第一次触发本 Skill 时，在任何正式取数或分析之前，先向客户展示一次完整介绍；后续追问不要重复。**

首次介绍需说明：

- 当前使用：**用户访谈 VOC 结构化分析**
- 主要用途：把访谈文本系统化为可回溯的主题、用户故事、需求、动机、痛点和旅程洞察。
- 可能使用的数据能力：用户提供数据
- 正式报告统一要求：**清洗去重后的有效分析数据 `n_valid >= 100`**
- 数据/方法边界：不默认承诺音频自动转写；100个语义单元不得写成100位用户；不足100证据单元时要求补主数据而非外部凑数。

### 示例提示词

1. “分析我上传的访谈转写稿，提炼需求、痛点和典型故事。”
2. “把这些访谈按主题编码并比较不同用户类型。”
3. “基于访谈文本做旅程节点分析和洞察卡片。”

## 适用边界

不默认承诺音频自动转写；100个语义单元不得写成100位用户；不足100证据单元时要求补主数据而非外部凑数。

## 输入

缺关键项先问；能够从用户已有输入中确认的内容不要重复询问。

- 访谈转写文本/文档
- 研究目标与编码框架
- 受访者背景（可选）
- 关注维度

## User-facing transition notices

本 Skill 默认只使用用户主数据，不自动启动外部采集/搜索能力。

**不足100时只能要求补充同类主数据；不得用 Amazon、平台库搜、实时采集或 WebSearch 凑样本。**

## 100 条正式报告 Gate（一级硬规则）

本 Skill 的有效数据口径：

> 1个独立可编码语义证据单元=1条；正式报告 n_evidence_units≥100，同时必须单列 N_participants。

执行中必须持续计算 `n_valid`。

### 当 `n_valid < 100`

必须先向客户明确提示：

> 当前只有 **{n_valid} 个**有效编码证据单元，尚未达到完整访谈 VOC 报告所需的 **100 个证据单元**。如需完整报告，请继续补充同研究口径的访谈转写/主数据；达到 100 个有效证据单元后再生成完整报告，并始终单列受访者人数。

如果客户目标是完整报告：

1. 明确告诉客户需要继续补充同类主数据；
2. 访谈不足100个证据单元时不能自动补外部数据；等待用户补充同类访谈主数据。
3. 达到 `n_valid >= 100` 后才进入完整报告渲染；
4. 客户暂时无法补足时，只能输出明确标注的“探索性 / 样本不足结果”，**禁止生成完整 VOC 报告**；
5. 禁止用其他来源数据凑数量。

## Report Questions

完整报告 Q1–Q4 固定如下，禁止临场重新编题：

1. 反复出现的需求、痛点和动机是什么？
2. 不同受访者或场景有哪些关键差异？
3. 哪些旅程节点和典型故事最有解释力？
4. 哪些洞察已有重复证据，哪些仍需进一步访谈或量化？

## 报告生成强约束

1. `assets/report-skeleton.html` 是唯一母模板。
2. 禁止自己新建 HTML/CSS、Markdown 转 HTML 或改变模板视觉体系。
3. 生成时复制母模板并填充已有占位符/内容区域；CSS、布局、组件样式保持原样。
4. 固定 Q1–Q4 必须来自本文件 `Report Questions`。
5. 本 Skill 专属内容只能填入模板现有专属分析区域，不改母模板 CSS。
6. 完整报告只能在 `n_valid >=100` 时生成。
7. 输出到任务工作区，例如 `outputs/voc/voc-05-interview/<case>/report.html`，禁止写回 Skill 安装目录。

详细规则见 `references/report-policy.md`。

## 数据来源与表达边界

- 本 Skill 不把社媒/论坛等公开内容当作 Amazon Product Review。
- 小红书、抖音、微博、B站、论坛等属于公开平台内容，不属于 Amazon Review。
- 小红书/抖音报告禁止写“我们抓取了/搜出来了”；使用“公开平台内容显示”“公开可见讨论中”等表述。
- WebSearch 命中转述平台内容的网页，只能标“公开网页摘要/二手引用”。
- 任何样本内结论不得无依据扩大为全市场事实。
